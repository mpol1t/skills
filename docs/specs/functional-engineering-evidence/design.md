# Design advice

Task: Assess eight interface, functional-contract, architecture, and prototype scenarios using the repository skills. Repository inspected read-only; no project spec or evaluation criteria read. No code changes or new frameworks proposed.

Grounding: `codebase-design/SKILL.md`, `FUNCTIONAL-CONTRACTS.md`, `DEEPENING.md`, `domain-modeling/SKILL.md`, `prototype/LOGIC.md`, `improve-codebase-architecture/SKILL.md`, and `tdd/SKILL.md` under `skills/engineering/`. These supply design principles; this advice does not initiate an architecture scan or prototype build.

1. **Empty `head` input.** `head(xs: number[]): number` lies when `[]` returns `undefined`. If emptiness is legitimate, use `head(xs: readonly number[]): number | undefined` and require callers to handle absence. For example, `[]` returns `undefined`, `[4]` returns `4`. If the domain requires a head, admit only a checked nonempty sequence, represented in TypeScript as `readonly [number, ...number[]]`, and return `number`. Validate external arrays before constructing that value; assertions do not establish nonemptiness. Assume normal dense numeric arrays, since arbitrary JavaScript values, sparse arrays, and mutable aliases need runtime handling. Do not invent a numeric fallback or leave an undocumented throw.

2. **Cyclic traversal and totality.** Exhaustive switching covers alternatives, not termination. If cycles are admitted and traversal may loop forever, it is partial. Specify cycle behavior: return a cycle rejection, or visit each node once with defined traversal semantics. For a finite graph, a visited set and bounded processing of each finite adjacency list give a termination argument. Alternatively, validate an acyclic finite structure and narrow the interface accordingly. State runtime resource assumptions, including recursion depth; tests and exhaustive typing cannot prove universal termination.

3. **Invoice purity.** The function is not pure. Calling an injected `clock.now()` acquires an observation, `Math.random()` adds hidden nondeterminism, and shared tax configuration mutation is observable state change. Injection improves visibility and substitution, not purity. Acquire time and random choices at an effect seam, then supply their values and an immutable tax snapshot to the calculation. Return an invoice and any intended configuration change as data; an executor owns applying changes. Verify that equal explicit inputs yield equal decisions and caller-owned data stays unchanged. A pure calculation can still make a wrong tax decision; business correctness remains a separate obligation.

4. **Local mutable lookup construction.** Accept this implementation when its clarity advantage is real. A local mutable `Map` followed by a frozen plain copy can preserve a pure observable contract without repeated copying. Record the clarity justification. Ensure no mutable aliases escape and caller-owned data is unchanged. `Object.freeze` is shallow: if values contain objects, they also need immutable ownership or appropriate copying/freezing. With the stated no-alias guarantee and immutable returned contents, local mutation is not an impurity visible to callers. Define duplicate-key behavior and the key representation as part of the lookup interface.

5. **Persisted brands and stale balance.** JSON does not carry trustworthy `PositiveAmount` evidence. Parse and check the value at entry, including numeric type, finiteness, positivity, and the domain's precision/range rules, before a checked constructor assigns the brand. A balance validated 30 seconds ago is an observation, not a current guarantee. At reservation or debit, enforce sufficient available balance atomically with the operation, using the existing transaction, conditional update, or reservation mechanism. A fresh read followed by an unprotected write still races. Keep malformed input, insufficient funds, and operational failure distinct; neither branding nor a timestamp establishes authorization to spend now.

6. **Reserve then charge effects.** Assuming a successful reservation is a precondition of charging, preserve that ordering. The reservation result must establish the quantity, identity, and validity required by the charge step. These operations are not assumed commutative, cacheable, or safe to repeat. Define durable operation identities and duplicate handling, reservation expiry, payment rejection, release/compensation, and recovery when a timeout leaves the remote result unknown. Reconcile an unknown outcome or use the provider's supported idempotency contract before retrying. Caching a past success is valid only as deliberate deduplication under that contract, not ordinary memoization of an effect. Cancellation also needs a rule for work already accepted remotely.

   At the orchestration interface, test successful ordering, reservation rejection preventing charge, payment rejection releasing or otherwise resolving the reservation, timeout after remote success, and duplicate retry producing no duplicate charge or reservation. These checks catch decision and coordination failures but cannot prove a fake adapter matches a real provider. Adapter contract/integration checks should establish provider idempotency and reconciliation behavior; a concurrency check at the inventory operation should establish prevention of over-reservation. Use existing mechanisms and distinct domain-rejection versus operational-failure outcomes, without adding an effect framework.

7. **Merging stable price operations.** Reject the stated justification. Small pure modules with stable domain interfaces and law tests can provide useful composition and protect invariants. Depth is leverage for callers, not implementation size. Apply the deletion test: would removing these interfaces eliminate complexity, or scatter their domain rules into checkout and its callers? A checkout module may improve orchestration locality while retaining those operations internally or as useful shared modules. Preserve their independent law/example evidence and add or retain integration coverage for orchestration. One passing E2E scenario does not subsume rounding, discount, or tax laws. Delete a test only when its contract is obsolete or its evidence demonstrably duplicated, not merely because it is called a unit test.

8. **Silent illegal reducer transition and prototype claims.** Purity and UI independence do not establish a correct transition contract or production readiness. An illegal transition should return a defined rejection; unchanged state is valid only if the domain explicitly specifies an intentional no-op for that action/state pair. Make that distinction visible through the reducer interface and the prototype's feedback. Manual exploration supports the design hypothesis, but production adoption still needs appropriate type checks, runtime validation of external state/actions, and behavioral verification of legal transitions, rejection cases, and invariant preservation. Keep time, randomness, persistence, and rendering in the driver. The portable logic can inform production implementation; the throwaway HTML shell and a few successful clicks are not production validation.
